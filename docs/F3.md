# Fase 3 — Feedback, diálogos y deshacer

Infraestructura de interacción: diálogos de confirmación, avisos con temporizador y deshacer, y estados de todos los controles. Sustituye a `confirm()`/`alert()` nativos y sienta la base que F4+ reutilizará para cada nueva acción permanente.

## Qué incluye

| Área                                    | Ubicación                                                             |
| --------------------------------------- | --------------------------------------------------------------------- |
| Diálogos de 3 niveles                   | `src/ui/dialog.ts`, `styles/components/dialog.css`                    |
| Avisos con temporizador y Deshacer      | `src/ui/toast.ts`, `styles/components/toast.css`                      |
| Estado de carga en botones              | `src/ui/loading.ts`                                                   |
| Estados globales de controles           | `src/styles/base.css`, `styles/components/buttons.css`                |
| Activación por teclado (Enter/Espacio)  | `src/app/actions.ts`                                                  |
| Aprobar/rechazar con diálogo + deshacer | `src/features/approvals/`                                             |
| Tests                                   | `tests/unit/{dialog,toast,actions}.test.ts`, `tests/unit/app.test.ts` |

## Diálogos (`ui/dialog.ts`)

Un único overlay compartido (`showDialog(options): Promise<boolean>`), tres niveles:

- **`info`** — un solo botón (Aceptar); Escape o el propio botón resuelven `true`. Para avisos, no para decisiones.
- **`confirm`** — Cancelar/Confirmar; Escape, clic en el fondo o Cancelar resuelven `false`. Para acciones reversibles.
- **`danger`** — igual que `confirm`, pero el botón de confirmación (rojo) nace **deshabilitado ~900 ms** con una barra que se vacía (`armDangerButton`, exportado para reutilizarlo fuera del diálogo genérico, como en el modal de rechazo). Es la fricción deliberada para acciones permanentes.

El foco por defecto nunca cae en el botón que confirma algo irreversible (va a Cancelar, o a Aceptar solo en el nivel informativo). El foco queda atrapado dentro del diálogo (Tab/Shift+Tab) y se devuelve al elemento que lo abrió al cerrarse. Abrir un diálogo mientras otro está abierto cancela el anterior.

## Avisos (`ui/toast.ts`)

`showToast(message, { kind?, durationMs?, undo? })`. Sustituye al antiguo `ui/notice.ts` (eliminado); `showNotice()` queda como alias fino para el código que no necesita más que un aviso simple.

- Barra de progreso (CSS `animation`) que se pausa **de verdad** (el temporizador de cierre en JavaScript se pausa junto con la barra) al pasar el cursor o el foco por encima — accesible por teclado, no solo con ratón.
- Botón **Deshacer** opcional: se ejecuta una sola vez y cierra el aviso de inmediato.
- Cola: como mucho 3 avisos visibles a la vez; el resto espera turno y aparece según se van cerrando los primeros.
- `role="status"` (o `"alert"` para `kind: 'error'`) dentro de una región `aria-live="polite"`.

## Deshacer, conectado a F1

La capa de datos ya tenía todo lo necesario desde F1 (`PostsRepository.latestAudit()` / `.undo()`, `organization_settings.undoWindowSeconds`); F3 es la primera vez que la interfaz lo usa: tras aprobar o rechazar, se pide la última entrada de auditoría y el aviso de éxito ofrece "Deshacer" durante `undoWindowSeconds` (8 s por defecto) — ni un segundo más ni menos que la ventana real de la base de datos, porque la duración del aviso se lee del mismo valor.

## Acciones permanentes conectadas

- **Aprobar**: diálogo `danger` → `withButtonLoading` en el botón → `repos.posts.approve()` → aviso con Deshacer.
- **Rechazar**: se rehízo el modal (antes era un formulario que no llamaba a nada): ahora exige un motivo, arma su propio botón de confirmación al abrirse (`armDangerButton`, el mismo primitivo del diálogo) y sí llama a `repos.posts.reject(id, reason)`.
- **Eliminar** y **marcar publicado** no tienen todavía ningún botón en la interfaz (esas pantallas son F4/F5/F6): quedan para conectarse con esta misma infraestructura cuando existan.

## Teclado y estados de los controles

- `app/actions.ts` delega también el teclado: cualquier `[data-action][tabindex]` activa con Enter/Espacio (los controles nativos como `<button>` ya respondían solos, así que se ignoran para no duplicar). Se revisó todo el árbol de la interfaz: prácticamente todo ya eran `<button>` reales; el único control puramente `<div>` sin acceso por teclado eran los `nav-item` del sidebar, que ahora llevan `tabindex="0" role="link"` y `aria-current="page"` en el activo.
- `base.css`: `:focus-visible` consistente en todos los controles (incluidos los `[tabindex]`), `:disabled` global (opacidad + `cursor: not-allowed` + `pointer-events: none`), y `prefers-reduced-motion` (con una excepción deliberada para la barra del aviso y la del botón armado: no son decorativas, comunican un tiempo real que sigue transcurriendo igual).
- `buttons.css`: `.btn.is-loading` + `.btn-spinner`; `ui/loading.ts` expone `withButtonLoading()` para envolver cualquier acción asíncrona sin tocar el resto del botón.

## Cómo probar

```bash
npm run check     # typecheck + lint + format + 144 tests
```

`tests/unit/dialog.test.ts` y `tests/unit/toast.test.ts` cubren ambos módulos de forma aislada con temporizadores simulados (niveles, armado, foco, pausa, cola, Deshacer). `tests/unit/app.test.ts` añade dos pruebas de extremo a extremo (memoria) para aprobar y rechazar, incluyendo el Deshacer real contra el repositorio.

## Decisiones

- Aprobar y rechazar se tratan como acciones **permanentes** (nivel `danger`), no meramente reversibles, aunque tengan ventana de deshacer: la fricción del botón armado es intencional (aprobar/rechazar tiene efecto real más allá de la ventana de 8 s), y el Deshacer es una red de seguridad adicional, no un sustituto de la confirmación.
- El rechazo reutiliza el modal existente (con textarea) en vez de forzarlo dentro del overlay genérico de `ui/dialog`, porque necesita un campo de formulario; para eso se expone `armDangerButton` como primitivo reutilizable fuera del diálogo.
- No se generalizó la focalización automática por teclado a todas las filas/tarjetas clicables (listings, templates, carrusel de fotos): la mayoría ya tiene un botón real equivalente dentro, y añadir un segundo punto de tabulación idéntico sería redundante. Quedó documentado aquí en vez de aplicarse a ciegas.

## Limitaciones conocidas

- Los E2E de Playwright se actualizaron (confirmación reforzada esperando a que el botón deje de estar `disabled`, motivo de rechazo, Deshacer) pero, igual que en F2, no se han podido ejecutar en este entorno por el bloqueo de red del sandbox a `cdn.playwright.dev`.
- No se auditó accesibilidad por teclado en filas de tabla ni tarjetas con un botón real anidado (ver Decisiones); si en el futuro se retira ese botón interno, habrá que revisar el acceso por teclado de la fila/tarjeta en sí.

## Entrega a F4

`ui/dialog`, `ui/toast` y `ui/loading` quedan listos para que el flujo completo de posts (crear, enviar, retirar, reabrir, eliminar, marcar publicado) los reutilice sin más infraestructura nueva: cada acción permanente es, en esencia, `showDialog({level:'danger', ...})` → `withButtonLoading` → llamada al repositorio → `offerUndo`.
