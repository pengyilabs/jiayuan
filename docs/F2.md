## Modelo

`profiles` gana `email`, `invited_at`, `confirmed_at`, `last_sign_in_at` (sincronizados desde `auth.users` con triggers; el rol sigue sin tocar `user_metadata`). El estado visible (`active` / `invited` / `disabled`) se deriva: sin confirmar → invitado; `active=false` → desactivado; si no, activo.

`organization_settings.require_admin_mfa` (por defecto `true`) exige que los administradores tengan una sesión **AAL2** (TOTP verificado); con AAL1 actúan como si no fueran administradores — nunca como empleados con privilegios de más. Un empleado nunca es administrador, tenga el AAL que tenga. El ajuste solo se cambia por SQL/`service_role`, no desde la aplicación.

`sign_in_attempts` (solo `service_role`) limita 5 fallos por usuario o 20 por IP en 15 minutos, para inicio de sesión **y** para solicitudes de restablecimiento (clave `reset:<identificador>`).

## Flujo de autenticación

1. **Login por usuario**: la Edge Function `sign-in` resuelve usuario→correo en el servidor (nunca en el cliente, para no enumerar cuentas), aplica el límite de intentos y llama a `signInWithPassword`; el cliente recibe el `access_token`/`refresh_token` y abre la sesión con `supabase.auth.setSession`.
2. **Invitación**: `invite-user` (solo admin) crea el usuario con `admin.inviteUserByEmail` y, si el rol es admin, asigna el rol con la identidad de quien invita (para que RLS y MFA se apliquen igual que a cualquier otra promoción). Si algo falla a mitad de camino, se revierte (se borra el usuario creado).
3. **Aceptar invitación / restablecer contraseña**: mismo formulario (`set-password`); el flujo (`invite` o `recovery`) se detecta por la URL de retorno de Supabase Auth.
4. **Desactivar/reactivar**: `set_user_active` (RPC, ya existía en F1) cambia `profiles.active`; `sync-user-access` refleja ese estado en Auth (bloquea/desbloquea al usuario) para que además no pueda renovar sesiones ya abiertas.
5. **MFA de administradores**: si `require_admin_mfa` y el administrador no tiene AAL2, la puerta de acceso pide el código si ya tiene un factor TOTP verificado, o fuerza el alta (QR + secreto) si es la primera vez.
6. **Inactividad**: `startIdleTimer` (30 min) cierra la sesión sin interacción del usuario.
7. **Guardas de ruta**: `canAccess(role, page)` decide qué páginas ve cada rol; el router (F0/F1) redirige e informa con un aviso. La navegación de administración (`data-role-only="admin"`) se oculta por CSS. Todo esto es solo interfaz: la seguridad real está en RLS/RPC (F1) y en `is_admin()` con AAL2 (F2).

## Cómo probar

```bash
npm run check                  # typecheck + lint + format + 123 tests (memoria + dobles de las funciones)
npm run functions:check        # typecheck de las Edge Functions con Deno
npm run db:test                # migraciones + pgTAP (incluye 070_auth_mfa_and_profiles, 22 aserciones)
npm run db:test:integration    # contrato de repositorios + adaptadores de funciones contra Postgres+RLS+PostgREST
```

`npm run db:test:integration` ahora también corre `tests/contract/functions-adapters.test.ts`: los adaptadores de las Edge Functions (directorio, límite de intentos, `is_admin()` con AAL2) contra PostgreSQL/PostgREST reales — no cubre las llamadas a Supabase Auth (GoTrue) en sí, que no forma parte de la emulación local (ver Limitaciones).

`npm run admin:create` crea el primer administrador o recupera el MFA de un usuario:

```bash
SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… npm run admin:create -- \
  --email zhuyan@homedirect.ca --username zhuyan --name "朱晏"
SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… npm run admin:create -- --reset-mfa --username zhuyan
```

Sin `--password` (o `ADMIN_PASSWORD`), genera una contraseña aleatoria y la muestra una sola vez.

## Decisiones

- El rol se asigna **siempre** con la identidad de quien realiza la acción (invitación o cambio posterior), nunca con `service_role`, para que RLS y la exigencia de MFA se apliquen igual en todos los casos — excepto el primer administrador (`create-admin`), que por definición no tiene a nadie que lo invite.
- `require_admin_mfa` es una bandera de organización, no de usuario: todos los administradores están sujetos a la misma política.
- El modo demo (`memory`) desactiva la exigencia de MFA y no tiene invitaciones por correo real: `invite()`/`resendInvite()` devuelven un enlace (`devLink`) que se muestra en la propia interfaz.
- Errores de login: usuario inexistente y contraseña incorrecta devuelven el mismo código (`invalid_credentials`), para no revelar qué usuarios existen.

## Limitaciones conocidas

- Las Edge Functions se han verificado con `deno check` y con tests unitarios (dobles en memoria de cada puerto) y, en `adapters.ts`, contra Postgres+RLS+PostgREST reales. Lo que **no** se ha probado end-to-end en este entorno (sin Docker) es el propio GoTrue (Supabase Auth): el envío real de invitaciones/recuperación, el intercambio de tokens de `signInWithPassword`, y el ciclo completo de enrolamiento TOTP contra un servidor Auth real. La lógica de cada handler está cubierta; falta la integración de extremo a extremo contra Auth.
- Los tests E2E (Playwright) se actualizaron para iniciar sesión antes de cada prueba (`loginAsAdmin`, y un caso con `liming` para el rol de empleado), pero no se han podido **ejecutar** en este entorno: la descarga del binario de Chromium está bloqueada por la lista blanca de red del sandbox (`cdn.playwright.dev`). Deben ejecutarse en CI o en un entorno con esa descarga permitida antes de dar F2 por cerrado end-to-end.
- El envoltorio de `npm run db:test:integration` para PostgREST no incluía `PGRST_DB_EXTRA_SEARCH_PATH=public,extensions` (a diferencia de `supabase/config.toml`, que sí lo trae desde F1); sin ese ajuste, `citext` deja de comparar sin distinguir mayúsculas a través de PostgREST. Ya corregido en `scripts/test-integration.sh`.
- `create-admin` con `service_role` es la única vía para el primer administrador (nadie puede invitarlo). Guarda `SUPABASE_SERVICE_ROLE_KEY` fuera del repositorio.
