# Fase 1 — Backend Supabase

Base de datos, seguridad y capa de datos. La interfaz sigue igual; ahora consume repositorios asíncronos.

## Qué incluye

| Área                            | Ubicación                                          |
| ------------------------------- | -------------------------------------------------- |
| 7 migraciones (esquema→RLS)     | `supabase/migrations/`                             |
| Semillas (catálogo + demo)      | `supabase/seed.sql`, `seed.demo.sql` (generadas)   |
| Tests de BD (pgTAP, 121 aserc.) | `supabase/tests/database/`, `supabase/tests/demo/` |
| Tipos generados                 | `src/types/database.ts`                            |
| Repositorios (memoria/Supabase) | `src/data/repositories/`                           |
| Contrato compartido de ambos    | `tests/contract/`                                  |
| Config de entorno               | `src/config/`, `.env.example`                      |

## Modelo de datos

`profiles` · `organization_settings` (fila única) · `listings` + `listing_media` · `platforms` + `post_types` + `post_type_groups` · `templates` + `template_variants` · `posts` + `post_media` · `audit_log` · `notifications` · y, **sin lógica hasta F9**, `social_accounts`, `publish_jobs`, `publish_attempts`.

- Textos traducibles en `jsonb` `{zh,en,fr,es}`; el cliente resuelve con `localize()` (idioma → en → zh → cualquiera).
- Fechas en `timestamptz` (UTC). El día de publicación se calcula en la zona de la organización (`America/Toronto`).
- Borrado lógico (`deleted_at`) con purga a los 30 días (`purge_deleted_posts()`, programada con pg_cron si existe).

## Permisos

| Acción                                | Empleado                 | Admin   |
| ------------------------------------- | ------------------------ | ------- |
| Ver posts                             | Solo los suyos           | Todos   |
| Crear post (siempre nace `draft`)     | Sí (a su nombre)         | Sí      |
| Editar contenido                      | Propio en draft/rejected | Todos   |
| Enviar / retirar / reabrir            | Autor                    | —       |
| Aprobar / rechazar / marcar publicado | No                       | Sí      |
| Eliminar (lógico)                     | Propio draft/rejected    | Sí      |
| Deshacer                              | Sus acciones             | Todas   |
| Propiedades, plataformas, templates   | Solo lectura             | CRUD    |
| Cambiar rol / desactivar usuarios     | No                       | Sí      |
| Tablas de publicación (F9)            | No                       | Lectura |

`anon` no tiene acceso a nada. El rol se lee **solo** de `profiles` (nunca de `user_metadata`); `handle_new_user` siempre crea `employee`.

**Estados** — `draft → pending → approved → publishing → published`; `pending → rejected → draft`; `publishing → failed → publishing|approved`. Un trigger impide saltos incluso con acceso directo.
**El cliente no puede escribir `status`, `approved_*`, `deleted_at`…** (privilegios por columna): solo las RPC `submit_post`, `withdraw_post`, `reopen_post`, `approve_post`, `reject_post` (motivo obligatorio), `mark_published`, `soft_delete_post`, `restore_post`, `undo_action`, `set_user_role`, `set_user_active`.

**Deshacer**: revierte la **última** acción del post, solo si la hizo quien llama (o un admin) y dentro de `undo_window_seconds` (8 s por defecto). Tras deshacer no se puede deshacer una acción anterior.

**Storage** — `post-media` (privado; ruta `<author_id>/<post_id>/<archivo>`; autor o admin) y `listing-media` (lectura pública; escritura admin). Límite 50 MiB; JPEG/PNG/WebP/MP4/MOV.

## Cómo probar

```bash
npm run check                  # typecheck + lint + format + 63 tests (memoria)
npm run db:seed:check          # el SQL de semillas coincide con src/data/seed
npm run db:test                # migraciones + pgTAP sobre un PostgreSQL local (variables PG*)
npm run db:test:integration    # contrato de repositorios contra Postgres+RLS+PostgREST reales
```

Con Docker: `supabase start && supabase db reset && supabase test db`, y `SUPABASE_TEST_URL=… SUPABASE_TEST_JWT_SECRET=… npm test` para el contrato contra Supabase.
`db:test` y `db:test:integration` emulan `auth`/`storage` (`supabase/tests/support/supabase_shim.sql`, solo para tests) y necesitan PostgreSQL con `pgtap`, `pgcrypto` y `citext`; el segundo, además, el binario de PostgREST (`POSTGREST_BIN`).

## Entornos

| Entorno    | Proyecto Supabase | Origen de datos                        |
| ---------- | ----------------- | -------------------------------------- |
| local      | `supabase start`  | `memory` (por defecto) o `supabase`    |
| staging    | proyecto propio   | `VITE_DATA_SOURCE=supabase` + URL/anon |
| producción | proyecto propio   | ídem                                   |

Despliegue de esquema: `supabase link --project-ref <ref>` y `supabase db push` (**no** aplica semillas). Tras cambiar el esquema: `npm run db:types`. Las semillas demo son solo para local.

## Decisiones

- Solo el **admin** escribe en propiedades, plataformas, templates y configuración (confirmado).
- `platforms.note` en en/fr replica la descripción, como el prototipo; **pendiente de traducir** (decisión: no traducir por ahora).
- Aprobaciones ya no son una lista aparte: se derivan de los posts `pending`.
- `platforms.connected/account_label` son transitorias; F9 las sustituye por `social_accounts`.

## Cambios visibles respecto a F0

- El nombre de la plataforma se traduce también en la vista de lista y en aprobaciones (antes siempre en chino).
- Editar una propiedad guarda el texto solo en el idioma activo (antes copiaba a zh y en).
- Con `es`, los textos sin traducción caen a inglés (antes a chino).
- Etiqueta "Seleccionar propiedad" traducida en aprobaciones (estaba fija en chino).
- Nuevos estados con etiqueta: aprobado, publicando, fallido.

## Limitaciones conocidas

- **Sin login hasta F2**: con `VITE_DATA_SOURCE=supabase` la app muestra una pantalla de error de arranque.
- `supabase/config.toml` y `seed.demo.sql` sobre auth real de Supabase **no se han validado con la CLI** (requiere Docker; no disponible aquí). Las migraciones y RLS sí se probaron en PostgreSQL 16 con emulación de `auth`/`storage`.
- Al purgar posts no se borran sus archivos de Storage (limpieza prevista en F4).
- `supabase-js` va en el bundle aunque se use `memory` (carga diferida pendiente).
- Las pruebas de la ventana de "deshacer" contra Supabase real están en pgTAP; el contrato no espera 8 s.

## Entrega a F2

Auth por invitación y usuario+contraseña, Edge Function `invite-user`, script `create-admin`, pantalla de login y guardas de ruta por rol (`addRouteGuard` ya existe). `set_user_role`/`set_user_active` y la protección del último admin están listos.
